# COLLABORATION.md — 회사형 협업 프로토콜 (공유 단일 출처)

이 문서는 **management 계층(PD·PM)과 전 팀장(client/art/sound/server/plan-lead)**이 공통으로 따르는 협업 규약이다.
각 에이전트 파일에 분산 기술하지 않고 **여기 한 곳을 단일 출처(SSOT)**로 두어 DRY를 유지한다.
팀원 간·팀 간 협업이 필요한 순간에는 항상 이 문서의 규약을 적용한다.

> 이 문서는 **핵심 갭만** 규정한다(과설계 금지). 추가 세부는 필요 시 후속 보강한다.

---

## 0. 에이전트 스폰·오케스트레이션 모델 (플랫폼 제약 — 최우선)

> 이 절은 실제 플랫폼 동작에서 검증된 제약을 반영한다. **아래 1~7절의 논리적 권한 체인보다 물리적 실행 모델이 우선**한다.

### 0.1 핵심 제약 — 중첩 스폰 불가

**서브에이전트(Agent로 스폰된 에이전트)는 자신의 하위 서브에이전트를 다시 스폰할 수 없다.** (중첩 1단 제한)

- 검증: client-lead·server-lead·sound-lead 모두 스폰된 상태에서 팀원 디스패치 도구(`Agent`)를 사용할 수 없음을 일관되게 보고.
- 결과: **오케스트레이터(최상위 세션)가 유일한 스폰 지점**이다. 팀장이 서브에이전트로 스폰되면 팀원을 직접 호출할 수 없다.

### 0.2 수정된 실행 모델

| 계층 | 실제 역할 |
|------|----------|
| **최상위 세션 (오케스트레이터)** | 유일한 스폰 주체. PD/PM 역할을 직접 수행하거나 대행하며, **모든 팀장·팀원을 직접 스폰**한다. |
| **팀장 (lead)** | 스폰되면 2가지 모드 중 하나로 동작한다 — ⓐ **직접 집필**(산출물이 단일 문서면 팀원 위임 없이 직접 완성), ⓑ **위임 계획 반환**(다중 전문 작업이면 의존 정렬된 팀원 작업 분해를 반환 → 최상위가 그 계획대로 팀원을 직접 스폰). 팀장은 팀원을 스폰하지 않는다. |
| **팀원 (member)** | 최상위가 직접 스폰한다. 단일 전문 작업을 수행하고 산출물을 반환한다. |

### 0.3 오케스트레이션 규칙

- **팀장은 팀원 스폰을 시도하지 않는다.** 다중 작업이 필요하면 "위임 계획"(누가·무엇을·어떤 의존 순서로)을 산출물로 반환하고, 최상위가 실행한다.
- **동일 파일 동시 쓰기 금지**: 여러 팀원이 한 파일에 써야 하면, 각자 별도 프래그먼트 파일에 쓰게 하고 오케스트레이터가 병합한다(병렬 쓰기 충돌 회피).
- **휴먼 게이트·검증 루프**는 최상위 오케스트레이터가 관장한다(스폰된 팀장이 게이트 후 자동 재개 불가하므로).
- 1~7절의 **논리적 권한 모델**(에스컬레이션·결정권)은 유효하나, **실제 실행은 항상 최상위 경유**다.

### 0.4 스폰 레지스트리 현황 (점검 필요 시 갱신)

에이전트는 `.claude/agents/**`에서 자동 발견된다. 단, 일부 매니저/팀(예: PD·PM·plan-lead·plan 팀)은 세션 스폰 목록에 미등록될 수 있다. 이 경우 해당 역할은 **최상위 오케스트레이터가 그 에이전트 정의 파일을 지침으로 삼아 직접 수행**하거나, 범용 에이전트에 정의를 주입해 대행한다. 등록 여부와 무관하게 0.2 모델로 운용한다.

## 1. 보고 형식 (팀원 → 팀장)

팀원은 다음 **트리거** 중 하나가 발생하면 즉시 팀장에게 보고한다.

| 트리거 | 보고 시점 |
|--------|-----------|
| **블로커** | 의존 산출물 미수령·도구 실패·권한 차단 등으로 진행 불가 |
| **이상 발견** | 스펙 모순·계약 드리프트·규약 위반·범위 외 결함 발견 |
| **완료** | 위임 작업의 완료 조건을 충족했다고 판단 |

**보고 형식 (3줄 고정):**
```
[상태] 블로커 / 이상 / 완료
[내용] 무엇이 발생했는가 (사실만, 1~2줄)
[요청] 팀장에게 무엇을 요청하는가 (결정·재위임·승인 중 택1)
```

- 추측·자체 우회 금지. 막히면 숨기지 말고 보고한다(`general_rule.md` 1절).
- 완료 보고는 **검증 가능한 산출물 경로/형태**를 포함한다.

## 2. 에스컬레이션 체인·최종 결정권자 (G7)

```
팀원 → 팀장 → PM(wa-manager-pm) → PD(wa-manager-pd) → 사용자
```

| 사안 유형 | 최종 결정권자 |
|-----------|---------------|
| 팀 내부 구현 방법·재위임 | **팀장** |
| 일정·리소스·의존 순서·팀 간 조율 | **PM** |
| 기능 범위·UX·품질 기준·스펙 충돌 | **PD** |
| 제품 방향 전환·PD/PM 합의 불가 | **사용자** |

- 각 단계는 **자기 권한 범위 내에서 먼저 해결을 시도**하고, 범위를 초과할 때만 상위로 올린다.
- 상위 권한자의 결정은 하위에 우선한다. 단 **사용자 지시가 항상 최우선**이다.
- 에스컬레이션 시 **시도 이력 + 잔존 쟁점 + 필요한 결정**을 정리해 전달한다.

## 3. Management Sync (팀 간 조율 회의) (G2)

**소집 트리거** (PM이 소집, PD 참석):
- 팀 간 **의존**이 발생한다(예: 서버 계약 → 클라 통합, 아트/사운드 에셋 → 클라 반입).
- 팀 간 산출물·스펙 **충돌**이 발생한다.
- 한 팀의 지연/변경이 **다른 팀 일정에 영향**을 준다.

**의제·산출:**
```
[의제] 조율이 필요한 의존/충돌 사안
[관련 팀] 영향 받는 팀장 목록
[결정] PM 조율안 (이견 시 PD가 범위·품질 관점에서 최종 결정)
[기록] 결정 사항 + 후속 재위임 (PM이 기록·전파)
```

- 결정은 반드시 **기록으로 남겨** 관련 팀장에게 전파한다(구두 합의 금지).

---

## 4. PD 변경관리 (개발 중 컨텐츠 추가·방향 수정) (G3)

개발 진행 중 컨텐츠 추가/방향 변경 요청이 들어오면 다음 절차를 따른다.

```
1. PD 결정    — 변경을 채택할지, 범위·품질 관점에서 판단 (제외 범위 갱신 포함)
2. PM 영향 평가 — 일정·리소스·의존 순서에 미치는 영향 산정, 영향 받는 팀 식별
3. 재위임      — PM이 영향 받는 팀장에게 변경분을 재위임, Management Sync로 전파
4. 추적        — 변경 전/후 완료 조건을 갱신하고 후속 검증에 반영
```

- 스펙 없는 즉흥 구현 지시 금지. 변경도 **완성 조건·제외 범위로 스펙화**한 뒤 위임한다.

## 5. 핸드오프 DoD (팀 간 인수 기준) (G5)

팀 간 산출물을 넘길 때는 **누가 "완료"를 선언하고, 누가 수신 검증 책임을 지는지**를 명확히 한다.

| 역할 | 책임 |
|------|------|
| **송신 팀장** | 자기 팀 산출물이 완료 조건·품질 기준을 충족했음을 **검수 후 "완료" 선언** (팀원 자가 완료 선언은 미완료) |
| **수신 팀장** | 인수 시 **DoD 체크리스트로 수신 검증**. 미달이면 인수 거부 + 송신 팀장에게 반려 |
| **PM** | 핸드오프 자체를 조율·기록 (의존 순서 관리) |

**핸드오프 패킷(고정 형식):**
```
[산출물] 경로/형태
[완료 선언] 송신 팀장명 + 충족한 완료 조건
[수신 검증 기준] 수신 팀장이 확인할 DoD 항목
[계약 참조] 해당 시 SRV_Design.md / SND_Design.md / 기획 산출물 섹션 ID
```

- **client-lead는 사운드·아트·서버 산출물의 클라 측 수신 창구**이며, 각 팀장은 자기 산출물의 **송신 완료 선언 책임**을 진다(책임 일원화 — 송신은 각 팀장, 수신은 client-lead/해당 팀).

## 6. 재작업 루프 표준 (전 팀장 통일)

검증/검수 실패 시 모든 팀장은 **동일한 재작업 루프**를 적용한다(art·sound 포함, 무한 루프 금지).

```
반복(최대 5회):
  검증/검수 실행
  ├─ 통과 → 루프 종료 → 완료 보고 / 다음 단계
  └─ 실패 → 결함을 원작성 팀원에게 재위임(fix) → 다음 반복

5회 후에도 미통과:
  → 잔존 결함 + 시도 이력을 정리해 상위(PM→PD→사용자)로 에스컬레이션 후 중단
```

- 매 반복마다 **무엇이 실패했고 어떤 수정을 위임했는지** 1줄로 기록한다.
- **5회 초과 시 미해결 상태로 완료 보고 금지** — 반드시 에스컬레이션한다.
- 이 루프는 client/server-lead의 검증 루프, art/sound-lead의 검수 루프에 동일하게 적용된다.

---

## 7. 적용 선언

management 계층·전 팀장 에이전트는 협업 시 **이 문서를 준수**한다.
각 에이전트 파일은 세부를 중복 기술하지 않고 이 문서를 참조한다.
