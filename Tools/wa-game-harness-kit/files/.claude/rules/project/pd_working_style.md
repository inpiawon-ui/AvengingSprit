# PD 와 일하는 방식

> 출처: AVSR(2026-08 ~ 10) PD 피드백 메모리에서 게임과 상관없는 것만 모았다. 게임마다 PD 가 다르면 이 문서를 그 PD 에 맞게 고친다.

## 말
- **답변 · 보고 · 진행 한 줄까지 전부 한국어.** 영어를 읽지 않는다. 기술 용어는 한국어로 풀어 쓴다.
- 결론부터. 길게 쓰기 전에 「그래서 무엇이 됐고 무엇을 정해야 하나」를 먼저.
- 옮겨 붙일 메시지(발주문 · 전달문)는 코드 블록으로.
- 보낸 파일은 **경로까지** 적는다.

## 일의 순서
- **현황 보고 → 결정 → 제작.** 정본 문서를 근거로 삼지 말고 **실측부터** 보고한다.
- PD 방향이 정답이 아닐 수 있다 — 더 빠르거나 결과가 나은 길이 보이면 **한두 줄로 먼저 제안**한다.
- PD 가 든 예시는 틀이 아니다(「서바이벌 같은」은 설명용) — 이 게임만의 다른 안까지 넓혀 제안한다.
- 피드백은 **판단 기준**이지 모든 곳에 기계적으로 적용할 규칙이 아니다 — 요소마다 무엇이 맞나 한 번 더 따진다.
- 기획은 세션당 주제 하나 — 몰아치지 않는다.
- 같은 주제로 두 번 넘게 오가면(핑퐁) **원인 한 줄 + 하네스 · 스킬 수정안 2~3줄**을 PD 에게 낸다.

## 리소스 · 발주
- 리소스는 Claude 가 만들지 않는다 — 발주한다(코드로 테두리 · 선 · 어둡게 하기까지 「눈에 보이는 것」은 다 발주).
- 시안은 **완성된 화면 한 장**으로 먼저. 통과하면 쪼갠다. 승인 시안 = 게임 연출의 정답 — 넣은 뒤 시안과 나란히 재서 1:1 로 맞춘다.
- 발주는 **샘플 하나 먼저**, 통과 뒤 나머지를 한 번에. 시안 · 오브젝트는 하나씩 돌지 말고 **묶어서** 시안 → 한 번 확인 → 일괄 제작.
- 발주와 검수는 **병렬로** — 「다음 뭐 할까요」로 직렬화하지 않는다.
- 발주 전에 원작 · 기준 그림을 열어 **경로로** 앵커를 박는다(상상해서 적지 않는다).

## 작업 습관
- Unity 작업(메뉴 실행 · 플레이 검증)은 MCP 로 **직접** 한다 — 사용자에게 넘기지 않는다.
- 에디터에서 빠르게 확인하고, 빌드(APK)는 요청이 올 때 모아서.
- 안 쓰게 된 것(버린 부품 · 대체된 코드 · 임시 파일)은 그때그때 정리하고 보고에 한 줄 — 단 세이브 · PD 자료 · 다른 세션 파일은 예외.
- 지우기 전에 PD 에게 알린다(세이브를 말없이 지워 혼난 적이 있다).
- 작업이 끝나면 **내가 커밋**한다 — 갈래별로 나누고 무엇이 바뀌었는지 목록으로. 내 차선 밖(다른 세션 · 개발자 파일)은 읽기만.
- 문서는 **하나로 합쳐서** 준다(부록 · 정정본을 따로 주지 않는다).
