## PM-MIL-001: 마일스톤 계획

> [WARNING] 마일스톤 날짜 변경 시 **전 파트 리드 + PD 승인** 필수. 일방적 변경은 다른 파트 일정에 연쇄 영향.

### 마일스톤 목록

| 마일스톤 | 목표 날짜 | 완료 기준 (DoD) | 담당 파트 |
|---------|---------|--------------|---------|
| **Pre-Production** | `[날짜]` | GDD 확정, 아트 디렉션 확정, TDD 초안, Vertical Slice 플레이 가능 | 전 파트 |
| **Alpha** | `[날짜]` | 핵심 게임 루프 완성, Critical 버그 ≤5, Alpha QA 기준 통과 | 전 파트 |
| **CBT (클로즈 베타)** | `[날짜]` | 콘텐츠 80% 구현, 성능 기준 충족, High 버그 ≤10 | 전 파트 |
| **OBT (오픈 베타)** | `[날짜]` | 콘텐츠 100%, 릴리즈 기준 충족, 스토어 사전 승인 | 전 파트 |
| **RC (Release Candidate)** | `[날짜]` | Critical 0 / High ≤3, 전 플랫폼 성능 통과, 스토어 제출 | QA + 개발 |
| **글로벌 출시** | `[날짜]` | 스토어 심사 통과, 서버 부하 테스트 완료, 운영팀 준비 완료 | 전 파트 |

### 마일스톤별 주요 산출물

| 마일스톤 | 기획 | 아트 | 클라이언트 | 서버 | QA |
|---------|------|------|----------|------|-----|
| Pre-Production | GDD v1, 코어루프 | 키비주얼, 스타일가이드 | 프로젝트 구조, 프로토타입 | 아키텍처 문서 | 테스트 계획 |
| Alpha | 콘텐츠 50%, 밸런스 v1 | 캐릭터 50%, UI 초안 | 핵심 시스템 구현 | API 기본 구현 | TC 50% |
| Beta | 전체 콘텐츠 | 전체 에셋 | 전체 기능 구현 | 전체 API | 회귀 테스트 |
| RC | 최종 밸런스 | 최종 에셋 | 최적화 완료 | 부하 테스트 완료 | 최종 QA |

## PM-SCH-001: WBS / 일정 관리

> 📌 **WBS(Work Breakdown Structure)**: 작업을 계층 구조로 분해한 일정 관리 체계.

### WBS 최상위 구조

```
[프로젝트명]
├── 1. Pre-Production
│   ├── 1.1 기획 (GDD, 코어루프, 시스템 설계)
│   ├── 1.2 아트 (스타일가이드, 키비주얼)
│   ├── 1.3 클라 (아키텍처, 프로토타입)
│   └── 1.4 서버 (아키텍처 설계)
├── 2. Alpha
│   ├── 2.1 코어 시스템 개발 (전투, 성장, 인벤토리)
│   ├── 2.2 핵심 UI 개발
│   ├── 2.3 서버 기본 API
│   └── 2.4 QA (Alpha TC)
├── 3. Beta
│   ├── 3.1 전체 콘텐츠 개발
│   ├── 3.2 최적화
│   ├── 3.3 현지화
│   └── 3.4 QA (전체 TC + 회귀)
└── 4. RC ~ 출시
    ├── 4.1 최종 버그 수정
    ├── 4.2 스토어 제출 준비
    └── 4.3 운영 준비
```

### 파트별 산출물 추적

| 산출물 | 담당 파트 | 담당자 | 착수일 | 완료 목표 | 상태 |
|--------|---------|--------|--------|---------|------|
| GDD v1 | 기획 | [이름] | [날짜] | [날짜] | 대기/진행/완료 |
| 스타일 가이드 | 아트 | [이름] | [날짜] | [날짜] | 대기/진행/완료 |
| 아키텍처 문서 | 클라/서버 | [이름] | [날짜] | [날짜] | 대기/진행/완료 |
| 전투 시스템 | 클라+서버 | [이름] | [날짜] | [날짜] | 대기/진행/완료 |
| `[산출물]` | `[파트]` | `[이름]` | `[날짜]` | `[날짜]` | 대기/진행/완료 |

## PM-SPR-001: 스프린트 운영

### 스프린트 세레모니 일정

> 📌 **스프린트**: 2주 단위 개발 사이클. 목표 기능을 집중 개발하는 반복 단위.

| 세레모니 | 주기 | 소요 시간 | 참석자 | 목적 |
|---------|------|---------|--------|------|
| 스프린트 계획 (Planning) | 격주 월요일 | 2시간 | 전 파트 리드 | 목표 설정, 태스크 분배 |
| 데일리 스탠드업 | 매일 | 15분 | 파트 내 | 진행 상황, 블로커 공유 |
| 스프린트 리뷰 | 격주 금요일 | 1시간 | 전 파트 + PD | 완료 기능 시연 |
| 회고 (Retrospective) | 격주 금요일 | 1시간 | 전 파트 | 개선사항 도출 |
| 파트 간 싱크 | 주 1회 수요일 | 30분 | 전 파트 리드 | 의존성 / 블로커 해소 |

### DoD (Definition of Done) — 공통 기준

> 📌 **DoD(Definition of Done)**: 작업 완료를 판단하는 명확한 기준. 임의 판단 금지.

- [ ] 기능 구현 완료 및 자체 테스트 통과
- [ ] 코드 리뷰 승인 1인 이상
- [ ] Unit Test 작성 및 통과 (신규 로직)
- [ ] 관련 문서 업데이트 (기획서, API 명세 등)
- [ ] QA 테스트 케이스 작성 완료 및 Pass
- [ ] `develop` 브랜치 병합 완료
- [ ] Missing Reference / 콘솔 에러 0개 (클라이언트 기능)

## PM-COM-001: 커뮤니케이션 계획

### 커뮤니케이션 채널 및 주기

| 유형 | 수단 | 주기 | 대상 | 내용 |
|------|------|------|------|------|
| 데일리 스탠드업 | 슬랙 또는 대면 | 매일 오전 10시 | 전 파트 | 완료 / 금일 계획 / 블로커 |
| 주간 빌드 공유 | 이메일 + Slack | 매주 금요일 | 팀 + 이해관계자 | 빌드 노트, 완료 기능, 다음 목표 |
| 마일스톤 보고 | 문서 + 회의 | 마일스톤마다 | PD + 이해관계자 | 달성 여부, 리스크, 다음 계획 |
| 긴급 이슈 | 전화 + Slack @channel | 즉시 | 관련 파트 리드 | Critical 버그, 서버 장애 등 |
| 파트 간 의존성 | 주간 싱크 회의 | 주 1회 | 전 파트 리드 | 블로커, 일정 조율 |

### 에스컬레이션 경로

```
이슈 발생
    ↓
담당 개발자 / QA 자체 해결 (1시간)
    ↓ (미해결)
파트 리드 개입 (4시간)
    ↓ (미해결)
PM 조율 (당일)
    ↓ (미해결)
게임 디렉터 / PD 결정
```

### 이해관계자 보고 주기

| 보고 대상 | 주기 | 수단 | 포함 내용 |
|---------|------|------|---------|
| 게임 디렉터 | 주 1회 | 대면 + 문서 | 진행 현황, 리스크, 의사결정 필요 사항 |
| 프로듀서(PD) | 격주 | 문서 + 회의 | 마일스톤 현황, KPI, 예산 |
| 이해관계자 | 마일스톤마다 | 프레젠테이션 | 게임 시연, 일정, 주요 이슈 |

| IP 라이센스 게임 | PM-MIL-001에 IP 홀더 승인 게이트(아트 방향성, 스토리, 마케팅 자료) 추가. 승인 리드타임 2~4주 버퍼 포함 |
| Live Ops | PM-MIL-001 출시 이후 마일스톤(시즌 패치, 이벤트 일정) 추가. 라이브 운영 스프린트 별도 정의 |
