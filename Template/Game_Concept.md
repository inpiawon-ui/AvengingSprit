## 0️⃣ 최우선 원칙 (모든 파트 공통 · 위반 불가)

### 🎯 원칙 1 — 원작 감성이 최우선이다

> **"AVENGING SPIRIT(1991, Jaleco 아케이드)의 게임 감성을 살리는 것이 디자인의 제1목표다."**

- 모든 아트·UI·이펙트·사운드 판단의 **최종 기준은 "원작다운가"** 이다.
- 모던함·트렌드·가독성이 원작 감성과 충돌하면 **원작 감성을 택한다.**
- HD 픽셀아트는 원작을 *대체*하는 것이 아니라 원작 해상도를 *복원·확장*하는 방향이다.
- 참조 우선순위: **① 1991 원작 아케이드 원본 → ② 제안서 목업 → ③ 현대 모바일 관습**

### 🎯 원칙 2 — 제안서 목업은 픽셀 단위 정답지다

- `Projects/AVSR/Reference/Mockups/` 의 화면 목업은 **레이아웃·색·배치의 확정 스펙**이다.
- 임의 재배치·색 변경·요소 추가 금지. 변경이 필요하면 **사유를 남기고 승인**을 받는다.
- ⚠️ 단, 목업은 **통짜 이미지(1장 JPEG)** 이므로 프로덕션 에셋(9-slice·아틀라스·스프라이트 시트)은
  목업을 정답지로 삼아 **새로 제작**한다. 목업 자체를 게임에 넣지 않는다.

## 1️⃣ CONCEPT

### 한 문장 설명
**방 기반 로그라이크 액션(궁수의 전설)** 에 **원작의 빙의(Possess) 시스템**을 결합하여,
장비가 아니라 **어떤 몸에 빙의했는가가 빌드를 결정**하는 세로형 모바일 액션 RPG.

### 타겟 플레이어

| 항목 | 값 |
|------|-----|
| 연령대 | 18~40세 (주), 13~17세 (부) |
| 게임 경험도 | 캐주얼~미드코어 |
| 경험한 유사작 | Archero, Archero 2, Survivor.io, Soul Knight |
| 부가 타겟 | 90년대 아케이드 레트로 팬 (Jaleco / Avenging Spirit 인지층) |

### 플랫폼

- [x] PC (Steam, 크로스플랫폼 — 후순위)

## 2️⃣ GAMEPLAY

### 핵심 게임루프

```
고스트(영혼·취약) → 호스트 선택/빙의 → 방 단위 자동전투 → 호스트 사망(육체 소멸)
   → 근처 적에게 재빙의 → 다음 방 진행 → 보스 → 다음 챕터(난이도 상승)
```

> **"장비가 빌드를 결정하지 않는다. 호스트가 결정한다."**
> **"모든 적이 당신의 다음 육체다."**

### 카메라 뷰 · 조작 — ✅ 확정

| 항목 | 확정값 | 비고 |
|------|--------|------|
| **카메라** | **완전 탑다운 (Top-down)** | 궁수의 전설과 동일. 제안서 p6 메인 플레이 목업과 일치 |
| **이동** | 가상 조이스틱 (좌하단) | 자유 8방향 이동 |
| **공격** | **오토 어택** (멈추면 발사) | 호스트별 공격 방식·사거리 상이 |
| **액션 버튼** | `POSSESS`(빙의) · `ULTIMATE`(얼티밋) | 우하단 2버튼 |

> ⚠️ **[해소된 충돌]** 제안서 p5 호스트 스탯의 `JUMP`는 탑다운에서 점프 개념이 성립하지 않는다.
> → **`JUMP` 스탯은 `DASH`(회피·이동기)로 재정의**한다. 목업 상 4스탯 레이아웃(HP/ATK/SPD/DASH)은 그대로 유지.

### 주요 메커닉

| 메커닉 | 설명 | 플레이어 반응 |
|--------|------|-------------|
| **빙의 (Possess)** | 고스트 상태에서 적에게 접근 → 빙의 버튼으로 그 적의 몸을 탈취 | "적이 곧 내 무기다" — 원작 고유 쾌감 |
| **호스트 교체** | 호스트 사망 시 즉사 아님. 고스트로 복귀 후 재빙의 | 실패가 곧 전환점 — 긴장과 회복 |
| **고스트 HP** | 고스트 상태 체력. 0이 되면 진짜 게임 오버 | 진짜 목숨은 영혼 하나뿐 |
| **12 얼티밋** | 호스트마다 완전히 다른 시그니처 필살기 | 12가지 다른 게임 |
| **로그라이크 버프** | 룸 클리어 시 3개 중 1개 선택, 해당 런 한정 | 매 런이 다른 빌드 |

## 6️⃣ PRODUCTION

### 기술 스택

| 항목 | 값 |
|------|-----|
| 엔진 | Unity (본 리포 GameFramework 3-tier 기반) |
| 언어 | C# · UniTask (Task/Coroutine 금지) |
| 에셋 | Addressable |
| 해상도 | 720×1280 세로 |

### 데이터 · 서버 정책 — ✅ 확정

> **"테이블 구조와 시스템은 처음부터 정상적으로 간다. 저장만 로컬로 시작해 나중에 서버로 교체한다."**

| 단계 | 방식 |
|------|------|
| **현재 (Phase 1~3)** | **로컬 저장 전용.** 유저 데이터는 `DataModule`(로컬 영속화)로 저장 |
| **추후** | 저장 구간만 서버 API로 교체. 게임 로직·테이블 구조는 **변경 없음** |

**필수 설계 제약 (재작업 방지):**
- 유저 데이터 접근은 **반드시 저장소 인터페이스를 경유**한다. 게임 로직이 로컬 파일을 직접 읽지 않는다.
- 로컬 구현체 → 서버 구현체 **교체만으로 전환**되어야 한다.
- 마스터 테이블(호스트·얼티밋·버프·챕터)은 **ScriptableObject 테이블 SO 1개에 배열**로 관리 (개별 asset 금지).
- 서버 전환 대비: 재화·진행도 갱신은 한 지점에 모아 둔다.

### 개발 일정 (제안서 기준 4개월)

| Phase | 기간 | 내용 |
|-------|------|------|
| 01 | 1개월 | 코어 시스템 — 빙의 메커니즘, 고스트 에너지, 기본 전투, 룸 진행 |
| 02 | 1개월 | 호스트 12 · 스테이지 챕터1~3 · 보스 · 적 AI |
| 03 | 1개월 | 로비·상점 UI · 배틀패스 · 수익화 · 성장 · 라이브서비스 |
| 04 | 1개월 | QA·폴리싱 · 소프트런칭 · 글로벌 런칭 (iOS·Android·Steam) |
