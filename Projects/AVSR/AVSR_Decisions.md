## 6. 데이터 설계 제약 (서버 전환 대비 — 필수)

1. 유저 데이터 접근은 **저장소 인터페이스를 경유.** 게임 로직이 로컬 파일을 직접 읽지 않는다
2. **로컬 구현체 → 서버 구현체 교체만으로** 전환되어야 한다
3. 마스터 테이블은 **테이블 SO 하나에 배열** (개별 `.asset` 금지)
4. 재화·진행도 갱신 경로는 **한 지점에 집약**
5. `UserData`에 **`saveVersion` 필수.** `unlockedHostKeys`는 저장하지 말고 progress로 매번 평가

## 9. 피격 동작 — 적용 후 재판단 (배치 1 테스트 항목)

**우려**: 피격 프레임이 들어가면 공격이 끊겨 보인다.

지금 코드가 정확히 그렇게 동작한다 — `Unit.TakeDamage` → `PlayHit()` 이 **재생 중인 공격을 잘라 먹는다**
(`PlayAttack` 은 피격 중이면 물러나는데, 반대 방향 보호는 없다).
람보처럼 연사가 빠른 호스트가 집중 사격을 받으면 공격 2프레임이 계속 잘려
"쏘는 자세가 안 나온다"로 보일 수 있다. 배치 1 테스트에서 이 지점을 본다.

판단 후 고를 수 있는 세 단계 — **그림은 어느 쪽이든 그대로 쓴다**. 재생 규칙만 바꾼다.

| | 동작 | 비용 |
|---|---|---|
| 가 | 지금 그대로. 피격이 공격을 자른다 | 0 |
| 나 | 피격 프레임은 **공격 중이 아닐 때만** 재생. 공격 중엔 붉은 점멸만 | 분기 1줄 |
| 다 | 피격 프레임을 아예 안 씀. 붉은 점멸로만 알림 | 분기 1줄 |

**그래서 `hit` 5장은 계속 받는다.** 방향당 1장이라 캐릭터당 5장뿐이고,
나중에 켜기로 결정했을 때 그림이 없으면 15종을 다시 돌려야 한다.
안 쓰기로 해도 손실은 5장 × 15종이고, 적 유닛 쪽에서는 공격이 성기므로 그대로 쓸 여지가 있다.

## 10. 정본 전환 — Developer Handoff v1.5 채택 (2026-08-11)

기획자가 넘긴 패키지 3종을 **AVSR 기획의 정본으로 채택한다.** 사본은
[`Canon/`](Canon/README.md) 에 넣었고 원본 ZIP 은 `기획 참고자료/` 에 있다.

문서 우선순위는 정본이 정한 것을 그대로 쓴다 —
**Runtime v1.5 > Host System v1.2 > Core Combat v3.1 > Experience Master v1.2 > Archive(사용 금지).**
값이 어긋나면 Runtime JSON 이 이긴다. 이 절이 기존 1~9절과 충돌하면 **이 절이 이긴다.**

### 10-1. 이미 맞는 것 — 건드리지 않는다

유령 HP 100 · 초당 −2 · 호스트 70% 시작 · 사망 빙의 20 · 이동 중 통상공격 OFF ·
보스 빙의 불가. 같은 Core Combat v3.1 계보라 `GameConfig.asset` 값이 그대로 일치한다.

### 10-2. 없어서 새로 넣어야 하는 것

| | 정본 | 지금 |
|---|---|---|
| **전술 빙의** | 살아 있는 호스트를 **유령 HP 6 · 쿨다운 8초** 로 교체 | 없음 (`TryPossess()` 가 비용을 안 받는다) |
| **빙의 조건** | 즉시 / 조건부(`BackAttack OR Down` 등 타입화) / 불가 3분류 | 전부 즉시, 우선순위만 |
| 빙의 채널링 | 0.35초 | 없음 |
| 유지 훅 | 호스트 12종마다 유지할수록 쌓이는 고유 게이지 | 없음 |
| 정지→발사 | 0.15초 | `_attackResumeSeconds: 0.12` — 맞춘다 |

전술 빙의가 빠지면 이 게임의 핵심 질문(“지금 유지할까, 바꿀까”)이 성립하지 않는다. **1순위다.**

### 10-3. 구조가 다른 것 — 단계적으로 간다

방 구성이 가장 크다. 정본은 **34개 방을 좌표까지 손으로 짠 레벨디자인**(스폰 104개,
좌표계 원점 좌하단·방 8.4×14 m)이고 우리는 절차적 생성이다. 절차적 생성은 **버린다**.
다만 임포터·방 생성기가 서기 전까지는 지금 것으로 플레이 검증을 계속한다 — 먼저 부수지 않는다.

미터 → 픽셀 환산은 임포터가 한 곳에서 처리한다. 게임 코드에 두 좌표계를 섞지 않는다.

### 10-4. 캐릭터 로스터 — 15종 → 정본 18적 / 12호스트

목업 15종과 정본 16종(원작)은 **10종이 같은 캐릭터**다. 확신 높은 대응:

| 우리 | 정본 | | 우리 | 정본 |
|---|---|---|---|---|
| `mafia` | E001 Gangster / H01 | | `wizard` | E010 White Wizard / H10 |
| `rambo` | E004 Thug | | `ninja` | E011 Ninja / H11 |
| `rambo_laser` | E007 Assault Gangster | | `vampire` | E014 Vampire / H15 |
| `dragon` | E003 Salamander / H03 | | `slugger` | E015 Baseball Player / H16 |
| `yogamaster` | E009 Guru / H09 | | `robot` | E008 Robot / H08 |

`snowwoman`·`amazoness`·`hitman`·`ninja_red`·`wizard_green` 는 대응이 없고,
정본에만 있는 것은 E005 그레네이더 · E006 마스터파이터 · E012 영매 · E013 미사일용병 ·
E016 드라군 · E017 방패병 · E018 센서드론 이다. **최종 대응표는 미결(10-6).**

### 10-5. 아트 순서를 스폰 수로 다시 잡는다

정본의 실제 스폰 104개를 세면 순서가 결정된다. **CH1 35스폰 중 26개(74%)가 갱스터·파이터**이고,
P0 목표 방인 `CH1_N01` 은 정확히 **갱스터 ×2 + 파이터 ×1** 이다.

| 챕터 | 1·2위 | 비중 |
|------|-------|------|
| CH1 | E001 갱스터 16 · E002 파이터 10 | 26/35 |
| CH2 | E007 어설트갱스터 6 · E001 갱스터 6 | — |
| CH3 | E002 파이터 6 · E018 센서드론 5 | — |

**12차 배치 1(람보+아마조네스)은 폐기한다.** 람보(Thug)는 CH1 에 3번뿐이고
아마조네스는 정본에 없다. 새 배치 1 = **갱스터(`mafia`, idle 5장 보유) + 파이터(신규)**.

또 하나 — 정본은 **적과 호스트의 요구 리소스가 다르다**(`Canon/Docs/CHARACTER_RESOURCE_SPEC.md`).
적은 Idle/이동/공격/피격/사망이면 되고, **호스트만** 궁극기 + 빙의 진입 + 빙의 이탈이 더 붙는다.
15종 × 35장 균등 배분이 아니라 **적 18종 기본 + 호스트 12종 추가**로 짠다.

### 10-6. 미결 — 사용자 확인 필요

1. **로스터 확정** — 목업에만 있는 5종(`amazoness`·`hitman`·`snowwoman`·`ninja_red`·`wizard_green`)을
   버릴지, 정본의 빈 슬롯(마스터파이터·미사일용병 등)에 배정할지. 이미 idle 5장씩 그려 둔 상태다.
2. **호스트 선택 화면** — 정본은 로비에서 12종 중 고르는 구조가 아니라
   **방 안에서 3역할 게이트로 시작 호스트를 고르는** 구조다(`CORE_GDD 01_CORE_OVERVIEW` 동기화 이력).
   지금 만든 `HostSelectPanel` 의 위치가 달라진다.
3. **잠금/해금** — 정본은 챕터 클리어 + 성장 노드(재화 4종)로 풀린다. 우리 `_unlockStage` 체계와 다르다.
