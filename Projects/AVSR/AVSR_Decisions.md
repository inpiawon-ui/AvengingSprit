## 6. 데이터 설계 제약 (서버 전환 대비 — 필수)

1. 유저 데이터 접근은 **저장소 인터페이스를 경유.** 게임 로직이 로컬 파일을 직접 읽지 않는다
2. **로컬 구현체 → 서버 구현체 교체만으로** 전환되어야 한다
3. 마스터 테이블은 **테이블 SO 하나에 배열** (개별 `.asset` 금지)
4. 재화·진행도 갱신 경로는 **한 지점에 집약**
5. `UserData`에 **`saveVersion` 필수.** `unlockedHostKeys`는 저장하지 말고 progress로 매번 평가

## 9. 피격 동작 — 적용 후 재판단 (배치 1 테스트 항목)

**우려**: 피격 프레임이 들어가면 공격이 끊겨 보인다.

지금 코드가 정확히 그렇게 동작한다 — `Unit.TakeDamage` → `PlayHit()` 이 **재생 중인 공격을 잘라 먹는다**
(`PlayAttack` 은 피격 중이면 물러나는데, 반대 방향 보호는 없다).
람보처럼 연사가 빠른 호스트가 집중 사격을 받으면 공격 2프레임이 계속 잘려
"쏘는 자세가 안 나온다"로 보일 수 있다. 배치 1 테스트에서 이 지점을 본다.

판단 후 고를 수 있는 세 단계 — **그림은 어느 쪽이든 그대로 쓴다**. 재생 규칙만 바꾼다.

| | 동작 | 비용 |
|---|---|---|
| 가 | 지금 그대로. 피격이 공격을 자른다 | 0 |
| 나 | 피격 프레임은 **공격 중이 아닐 때만** 재생. 공격 중엔 붉은 점멸만 | 분기 1줄 |
| 다 | 피격 프레임을 아예 안 씀. 붉은 점멸로만 알림 | 분기 1줄 |

**그래서 `hit` 5장은 계속 받는다.** 방향당 1장이라 캐릭터당 5장뿐이고,
나중에 켜기로 결정했을 때 그림이 없으면 15종을 다시 돌려야 한다.
안 쓰기로 해도 손실은 5장 × 15종이고, 적 유닛 쪽에서는 공격이 성기므로 그대로 쓸 여지가 있다.

## 10. 정본 전환 — Developer Handoff v1.5 채택 (2026-08-11)

기획자가 넘긴 패키지 3종을 **AVSR 기획의 정본으로 채택한다.** 사본은
[`Canon/`](Canon/README.md) 에 넣었고 원본 ZIP 은 `기획 참고자료/` 에 있다.

문서 우선순위는 정본이 정한 것을 그대로 쓴다 —
**Runtime v1.5 > Host System v1.2 > Core Combat v3.1 > Experience Master v1.2 > Archive(사용 금지).**
값이 어긋나면 Runtime JSON 이 이긴다. 이 절이 기존 1~9절과 충돌하면 **이 절이 이긴다.**

### 10-1. 이미 맞는 것 — 건드리지 않는다

유령 HP 100 · 초당 −2 · 호스트 70% 시작 · 사망 빙의 20 · 이동 중 통상공격 OFF ·
보스 빙의 불가. 같은 Core Combat v3.1 계보라 `GameConfig.asset` 값이 그대로 일치한다.

### 10-2. 없어서 새로 넣어야 하는 것

| | 정본 | 지금 |
|---|---|---|
| **전술 빙의** | 살아 있는 호스트를 **유령 HP 6 · 쿨다운 8초** 로 교체 | 없음 (`TryPossess()` 가 비용을 안 받는다) |
| **빙의 조건** | 즉시 / 조건부(`BackAttack OR Down` 등 타입화) / 불가 3분류 | 전부 즉시, 우선순위만 |
| 빙의 채널링 | 0.35초 | 없음 |
| 유지 훅 | 호스트 12종마다 유지할수록 쌓이는 고유 게이지 | 없음 |
| 정지→발사 | 0.15초 | `_attackResumeSeconds: 0.12` — 맞춘다 |

전술 빙의가 빠지면 이 게임의 핵심 질문(“지금 유지할까, 바꿀까”)이 성립하지 않는다. **1순위다.**

### 10-3. 구조가 다른 것 — 단계적으로 간다

방 구성이 가장 크다. 정본은 **34개 방을 좌표까지 손으로 짠 레벨디자인**(스폰 104개,
좌표계 원점 좌하단·방 8.4×14 m)이고 우리는 절차적 생성이다. 절차적 생성은 **버린다**.
다만 임포터·방 생성기가 서기 전까지는 지금 것으로 플레이 검증을 계속한다 — 먼저 부수지 않는다.

미터 → 픽셀 환산은 임포터가 한 곳에서 처리한다. 게임 코드에 두 좌표계를 섞지 않는다.

**12차 배치 1(람보+아마조네스)은 폐기한다.** 람보(Thug)는 CH1 에 3번뿐이고
아마조네스는 정본에 없다. 새 배치 1 = **갱스터(`mafia`, idle 5장 보유) + 파이터(신규)**.

또 하나 — 정본은 **적과 호스트의 요구 리소스가 다르다**(`Canon/Docs/CHARACTER_RESOURCE_SPEC.md`).
적은 Idle/이동/공격/피격/사망이면 되고, **호스트만** 궁극기 + 빙의 진입 + 빙의 이탈이 더 붙는다.
15종 × 35장 균등 배분이 아니라 **적 18종 기본 + 호스트 12종 추가**로 짠다.

### 10-6. 미결 — 사용자 확인 필요

1. **로스터 확정** — 목업에만 있는 5종(`amazoness`·`hitman`·`snowwoman`·`ninja_red`·`wizard_green`)을
   버릴지, 정본의 빈 슬롯(마스터파이터·미사일용병 등)에 배정할지. 이미 idle 5장씩 그려 둔 상태다.
2. **호스트 선택 화면** — 정본은 로비에서 12종 중 고르는 구조가 아니라
   **방 안에서 3역할 게이트로 시작 호스트를 고르는** 구조다(`CORE_GDD 01_CORE_OVERVIEW` 동기화 이력).
   지금 만든 `HostSelectPanel` 의 위치가 달라진다.
3. **잠금/해금** — 정본은 챕터 클리어 + 성장 노드(재화 4종)로 풀린다. 우리 `_unlockStage` 체계와 다르다.

## 11. 성장·해금 전환 — 파편 방식 채택 (2026-08-27)

**확정 #22 의 해금 조건과 10-6 의 미결 3(잠금/해금)을 여기서 대체한다.**
상세 설계는 [`_exchange/out/42_jobs/AVSR_HostSkills.md`](_exchange/out/42_jobs/AVSR_HostSkills.md) v0.4.

### 11-1. 해금 — 진행도에서 파편으로

| | 이전 (확정 #22) | 변경 |
|---|---|---|
| 해금 조건 | `StageReach` / `ChapterBossClear` **2종만** | **호스트 파편** |
| 봉인된 몸 | (인게임 제약 없음) | **빙의는 된다. 스킬만 안 나온다**(평타만) |

빙의 자체를 막지 않는 이유 — 빙의는 눈앞의 적으로만 하는데 방 구성은 유저가 못 고른다.
봉인된 적만 나오는 방이 생기면 손쓸 도리 없이 죽는다.

**파편이 진행도 게이팅을 겸하므로 챕터 조건이 없어도 잠긴다** — 뱀파이어는 CH2~3 에만
나오므로 CH1 에서는 뱀파이어 파편을 얻을 수 없다.

### 11-2. 레벨은 둘이고, 능력치 표는 호스트가 갖는다

| | 담당 |
|---|---|
| **고스트 Lv** | **레벨** — 빙의하면 그 호스트가 그 레벨로 동작한다. **고스트에 스탯은 없다** |
| **호스트 레벨 표** | 그 레벨에서 HP·ATK 가 얼마인가 (호스트별 배열) |
| **호스트 숙련도 Lv1~10** | 그 몸의 **스킬** (능력치 아님) |

호스트마다 레벨이 따로 쌓이면 "키운 몸이 방에 없다 → Lv1 몸을 탄다 → 죽는다 →
**빙의를 피하게 된다**" 가 되어 핵심 재미가 죽는다. 레벨은 고스트가 준다.

### 11-3. 파편 획득 — 빙의를 벌주지 않는다

| 어떻게 했나 | 파편 |
|---|---|
| 그냥 죽였다 | 1 |
| **빙의해서 쓰다가 잃었다** | **3** |

파편이 "죽이면만 나온다" 면 `파편이 필요하다 → 죽여야 한다 → 빙의하면 안 된다` 가 되어
파밍이 핵심 재미를 막는다. 이 차등이 설계의 핵심이다.

### 11-3b. 등급과 등장 빈도는 다른 축이다

**등급은 캐릭터의 능력이다. 등장 빈도가 아니다.** 드라군이 CH3 에 1마리뿐인 것은
드라군이 특별해서가 아니라 레벨 디자인이 그런 것뿐이다.

| 축 | 정하는 것 | 푸는 문제 |
|---|---|---|
| **등급** = 액티브 스킬의 세기 | 파편 **요구량** 배수 | 센 몸은 오래 걸린다 |
| **등장 빈도** | 파편 **드롭 수** | 드물게 나오는 몸도 모을 수 있다 |

등급은 **`HostTable._grade` 칸(B / A / S)으로 손수 배정한다.** 쿨에서 도출하지 않는다 —
플레이하며 조정할 축이라 손으로 잡는 쪽이 낫다. 이미 구현되어 있고 시작 호스트를
데려가는 골드 비용에도 쓰인다(B 300 / A 600 / S 1000).
파편 요구량 배수는 B ×0.8 / A ×1.2 / S ×1.8.

기본 능력치로 등급을 매기지 않는다 — `AVSR_JobClasses.md` 가 DPS 를 직업 안에서
일부러 맞춰놨기 때문에 능력치로 뽑으면 "격투는 다 S" 가 된다.
**액티브 스킬이 판을 얼마나 뒤집는가**로 잡는다.

### 11-3d. 스탯 — 6종, 전부 성장한다

**HP · 공격력 · 치명타 확률 · 공격속도 · 사거리 · 이동속도**

`_possessHpPercent`(빙의 시작 HP%)는 **스탯이 아니다. 표시하지 않는다.**
나머지 6종은 "이 몸의 능력" 인데 그것만 "뺏을 때의 조건" 이라 층이 다르고,
0~100 바로 그리면 높을수록 좋은 것처럼 읽힌다. 뺏으면 HP 바에 즉시 보이므로
미리 숫자로 알려줄 이유도 없다. 데이터로만 남긴다.

**`DASH` 를 폐기한다.** 전투 코드 어디에도 쓰이지 않고(`HostSelectPanel.cs:378` 이 바만 그린다),
`CanonImporterV23.cs:136` 이 **DASH 칸에 공격속도 값을 넣고 있어** 유저가 보는 숫자가 거짓말을 한다.
확정 #2 의 `JUMP → DASH(패시브 회피)` 는 **회피가 화면에서 안 보인다**는 이유로 여기서 폐기한다.

**`사거리` 를 표시 스탯에 넣는다.** 이 게임에서 몸을 가르는 1순위 값인데 유저에게 안 보였다.
성장은 **자기 직업 밴드 안에서만** — 넘으면 직업이 무너진다.

**치명타**: 확률만 스탯(초기 10%), 배율은 전역 고정 ×2.0. 둘 다 스탯이면 곱해져 폭주한다.
연출은 색 변경 + 글자 확대(`DamageText` 가 이미 색을 파라미터로 받는다).

**주 성장 스탯 2개** — 호스트마다 2개만 크게 오르고 나머지는 조금 오른다.
23가지 패턴은 못 외우고, 직업 단위로만 나누면 직업 안 6명이 또 같아진다. **2개면 외운다.**
구간별로 오르는 스탯이 바뀌는 방식은 **쓰지 않는다** — 성장 계획을 못 세우고,
리듬은 이미 숙련도 Lv5(특수 효과 해제)가 만들고 있다.

⚠️ 로비 스탯 표시가 **4칸 → 6칸**이 된다. 목업 예외 승인 항목.

### 11-3c. 수치는 전부 잠정이다 — 구조가 목표다

지금 정한 수치(파편 곡선 · 등급 배수 · 드롭 보정)는 **플레이 조정 대상**이다.
구조의 목표는 **코드를 안 고치고 모든 값에 손이 닿는 것** 하나다.

⚠️ 10절의 `_rangeMul` 계열처럼 **조정하려고 만든 칸이 죽는 사고**를 반복하지 않는다.
파생값(등급 · 드롭 보정 · 해제 여부 · 직업)은 **저장하지 않고 계산한다.**
상세: `AVSR_HostSkills.md` §10.

### 11-4. 용어 — 얼티밋 폐기

**"얼티밋 · 필살기 · 궁극기" 를 쓰지 않는다.** 액티브 스킬 · 패시브 스킬 · 특수 효과 셋만 쓴다.
현행 얼티밋은 이미 14초 쿨다운 버튼이므로 **새 시스템이 아니라 내용 교체**다.
인게임 버튼은 2개 그대로이고 **목업 예외가 필요 없다.**

지금은 다르다. 그 기획은 빠진 것과 어긋난 것이 많아 **처음부터 다시 잡고 있다.**

- **목업에 있는 것을 다르게 그리는 것만 예외다.** 이때만 승인을 받는다.

**아트 제1원칙(확정 #1, 1991 원작 감성 재현)은 그대로 최우선이다.**
오히려 더 명확해진다 — 목업이 "감성의 기준" 이라는 본래 역할에 집중하게 된다.

> *"이 절이 기존 1~9절과 충돌하면 이 절이 이긴다"* 고 선언했는데,
